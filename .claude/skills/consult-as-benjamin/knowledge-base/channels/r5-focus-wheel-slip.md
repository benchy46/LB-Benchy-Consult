# #r5-focus-wheel-slip
**Slack channel ID:** C0AJ30S0SEA
**Purpose:** Focused cross-functional (Mech/Autonomy/QA) working channel to root-cause and fix R5's traction wheel slip problem (especially on wet floors at max water/suction settings). Benjamin is named the **Mechanical DRI** for this issue (Jeremy Tan = Autonomy DRI, Yufei Guo = QA DRI). Channel runs 2026-03-03 (creation) to 2026-07-06 (last observed activity), fully captured in one page (no pagination needed).

## Decisions & Reasoning (Benjamin)
- **Defined the wheel-slip mitigation/recovery control loop concept**: "For now we can simulate wheel slip by simply pulling the robot back manually. Therefore our objective now should be detecting wheel slip and then doing the respective controls to prevent slipping." He laid out the loop explicitly: `Wheel slip detected -> Reduce torque/velocity -> Wheel slip not detected -> Increase torque/velocity slowly by a specified rate -> wheel slip detected -> Loop` — 2026-03-05 — [source](https://lionsbot.slack.com/archives/C0AJ30S0SEA/p1772706812750169)
- **Identified suction as the primary lever for recovery, and pushed to make it fully adjustable rather than constrained to user-facing presets**: "To recover, just reduce suction. It will be best to not limit to the user's input, means you can throttle suction to any value you want." He also pinpointed the worst-case condition empirically: "At max water settings with max suction, wheel slip occurs the most often," and proposed removing user-facing water spray setting 6 as a mitigation, while keeping other cleaning settings unchanged for users — 2026-03-03 — [source](https://lionsbot.slack.com/archives/C0AJ30S0SEA/p1772509562801759)
- **Insisted hands-on physical testing was required rather than a spec handoff**: when Jeremy Tan asked for "exact values to use" so the team could expose settings on the touchscreen without him, Benjamin was direct: "I need to be beside you, with the robot, to try physically... We do not know any exact values. we need to be together with the robot to actually try." He then gave a concrete starting point once pressed: try suction at 20% or 17%, combined with torque/speed control — 2026-03-03 — [source](https://lionsbot.slack.com/archives/C0AJ30S0SEA/p1772510015583309)
- **Held firm that slip detection is a hard blocking prerequisite for the recovery/closed-loop system**, against pushback from Joei Wee who wanted to parallelize development to save time. Benjamin's reasoning, delivered in short, insistent turns: "If slip detection is not done, we cannot solve the rest... How to validate if the other solutions work? We know reducing speed helps, we know reducing suction helps. Then we are stuck already... we can only validate if the system knows slip is happening, and can calculate that the slip has actually reduced by quantifying the slip." He did concede a partial parallelization path when Joei pushed further ("You can minimally write something that takes in the slip detection as input, then adjust the other parameters accordingly") but maintained that true validation needs the detection signal first — 2026-03-10 — [source](https://lionsbot.slack.com/archives/C0AJ30S0SEA/p1773134584414109)
- **Proposed upgrading recovery control from simple bang-bang to multi-step ("multi-bang")**: "for wheel sleep recovery, are we not able to do more intelligent traction wheel control? Like further reduce speed if initial recovery settings don't work? Now we are doing simple bang bang control for recovery. Can we change to multi bang?" — pushing the software recovery strategy toward finer-grained control rather than a single on/off response — 2026-04-29 — [source](https://lionsbot.slack.com/archives/C0AJ30S0SEA/p1777424358097629)
- **Synthesized a full status/plan covering CM preload QC, SW detection/recovery state, and root-cause attribution** across suspension preload, wheel tread friction, and cleaning settings, with a to-do list including slope testing and a proposed CM QC script (accelerate robot from static to 1.0 m/s over 2m and observe velocity/pitch profile to catch bad suspension assembly) — a structured, multi-owner action plan rather than a single fix — 2026-04-29 — [source](https://lionsbot.slack.com/archives/C0AJ30S0SEA/p1777433885755919)
- **Confirmed CM now has a physical, measurable go/no-go criterion for suspension preload** (measuring thread length to adjust preload to spec 15) rather than a subjective assembly step — 2026-04-29 — [source](https://lionsbot.slack.com/archives/C0AJ30S0SEA/p1777445524811649)

## Recurring Themes / Principles Observed
- Treats "detect the problem" as a strict prerequisite before "fix the problem" — you cannot validate a mitigation without first being able to measure the thing you're mitigating.
- Prefers physically testing with the robot in person over prescribing values remotely/theoretically ("we do not know any exact values... we need to be together with the robot to actually try").
- Breaks down root cause into controllable vs. uncontrollable/degrading factors (suspension preload is controllable and stable if maintained; wheel tread friction wears down over time; cleaning settings are software-controllable) rather than treating wheel slip as one undifferentiated problem.
- Converts subjective assembly/QC steps into measurable, testable criteria (preload thread-length spec, proposed pitch/velocity QC script) — consistent with his pattern elsewhere of preferring quantifiable acceptance criteria.
