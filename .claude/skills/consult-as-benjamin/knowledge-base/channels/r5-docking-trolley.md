# #r5-docking-trolley
**Slack channel ID:** C0AJ8JU0DGF
**Purpose:** Design/engineering channel for the R5 "docking trolley" (a mobile water-refill/refuel cart accessory) — CAD reviews, tank material/molding decisions (3DP vs vac-cast vs rotomold), connector and float-switch design, and prototype failure troubleshooting. Channel runs 2026-03-05 (creation) to present (2026-07-24), fully covered in two fetches. Benjamin is cc'd on nearly every CAD/design review as a standing reviewer, though he posts substantive replies less often than he's tagged.

## Decisions & Reasoning (Benjamin)
- **Proposed detecting trolley connection via existing float-switch signals instead of adding a dedicated sensor/connector pin**: when Lucas noted an extra connector pin would be needed "by right" for trolley detection, Benjamin suggested "there maybe a clever way to use the float switch inputs to detect it" — specifically, treating the combination of "top switch triggered + bottom float switch untriggered" as a logically impossible state unless the trolley is connected, and using that as the detection signal. Akhil independently supported the same direction, noting his home robot vacuum uses the same trick (combining "clean tank empty" and "trolley not installed" error states). This mirrors the same engineering instinct seen elsewhere: prefer inferring a state from signals that already exist over adding new hardware — 2026-03-09 — [source](https://lionsbot.slack.com/archives/C0AJ8JU0DGF/p1773056639028809)
- **Chose the fiberglass-wrap repair over the 3DP-clamp-and-epoxy repair** for a cracked 3D-printed prototype tank: "Proposal 2 is better, 3DP clamps of that size isn't the best for that size" — rejecting the mechanical-clamp approach specifically on the grounds that 3D-printed clamps wouldn't hold up at that scale, favoring the full fiberglass/epoxy composite wrap instead — 2026-07-13 — [source](https://lionsbot.slack.com/archives/C0AJ8JU0DGF/p1783921820040709)
- **Raised integration/space concern about consolidating pumps and the ultrasonic driver into the docking station tray**: floated the idea of "the whole robot going in the tray" for cleaning (potentially including brushes), then flagged the practical constraint himself: "If we want to integrate the extra pumps and ultrasonic driver all into the docking station, I think cmi, no space" — raising an ambitious concept but immediately pressure-testing it against a concrete space constraint — 2026-05-26 — [source](https://lionsbot.slack.com/archives/C0AJ8JU0DGF/p1779759058043219)
- **Checked for a real-world handling requirement (forklift compatibility)** on the trolley design: "Just want to check if our tolley design accounts for using a fork lift to go under and lift it?" — a logistics/handling consideration raised proactively rather than left to be discovered later (Akhil's answer: not a stated requirement) — 2026-05-04 — [source](https://lionsbot.slack.com/archives/C0AJ8JU0DGF/p1777889764101799)
- **Flagged a UX/ergonomic clearance issue on the connector module CAD**: "Will need to adjust this surface here, because we will need space for the users fingers to lift up the clean water top up lid" — a hands-on, user-interaction-level catch on an industrial design iteration — 2026-06-03 — [source](https://lionsbot.slack.com/archives/C0AJ8JU0DGF/p1780467897091559)

## Recurring Themes / Principles Observed
- Consistent preference for solving a new requirement (trolley detection) by reusing existing signals/hardware rather than adding new sensors or connectors.
- Willing to float an ambitious integration idea (whole-robot-in-tray cleaning) but self-corrects with a concrete constraint (space) rather than letting it run unchallenged.
- Practical, logistics-and-usability-minded catches (forklift handling, finger clearance for a lid) alongside pure mechanical/materials judgment (clamp size vs. fiberglass wrap) — his input spans from shop-floor practicality to structural material choices.
